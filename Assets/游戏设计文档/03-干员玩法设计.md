# 干员玩法设计

> 参考明日方舟肉鸽（集成战略）模式，结合本项目已有架构（OperatorData / DeploymentManager / RogueRuntimeState / 天赋卡 / 金币商店 / StS 分叉地图），设计一套完整的干员持有、获取、升级、升星系统。

---

## 一、设计概述

### 1.1 现状与问题

| 现状 | 问题 |
|------|------|
| 29 个 OperatorData 资产，战斗时全部可用 | 玩家无需选择，每关可用所有干员，无策略取舍 |
| OperatorCard 固定在场景中（角色画布/角色商店处） | 无法动态切换干员阵容，关卡间无成长感 |
| 天赋卡系统（96 张）提供局内成长 | 成长只作用于"数值加成"，没有"干员本身变强"的体感 |
| 天赋树系统提供永久成长 | 永久成长与局内成长割裂，缺乏中间层的"干员养成" |
| GoldShop 只卖天赋卡 | 商店功能单一，缺乏"招募干员"这一核心肉鸽体验 |
| 同一干员可无限重复购买部署，可多实例同时在场 | 刷一个最强干员即可，招募多样干员失去意义；升级属性多实例叠加数值失控 |

### 1.2 设计目标

1. **初始阵容**：每局开始玩家拥有一小队固定初始干员（3~4 名），而非全部 29 名
2. **局内招募**：在商店/事件节点可以招募新干员，扩充阵容
3. **干员升级**：消耗局内资源提升干员等级，增强基础属性
4. **干员升星**：消耗局内资源进行精英化，解锁等级上限和额外能力
5. **阵容上限**：携带干员数量有上限，形成策略取舍
6. **单实例部署**：每名干员同时只能 1 个在场，撤退/阵亡后需等再部署冷却才能重新部署（明日方舟式），让招募多样干员成为策略必需

### 1.3 核心设计原则

- **不破坏现有战斗循环**：OperatorCard 拖拽部署、DP 费用系统、OperatorUnit 战斗逻辑保持不变
- **局内系统优先**：所有干员养成均为局内行为，通关/死亡后清零（与天赋卡一致），不引入永久干员等级
- **复用现有货币**：金币（RunGold）作为干员招募/升级的主要货币，新增"希望"作为阵容容量货币
- **与天赋卡互补**：天赋卡 = 全队/职业/专属的数值加成；干员升级 = 单个干员的基础属性成长。两者叠加生效

### 2.1 星级定义

## 三、局内干员持有系统

### 3.1 干员名册（OperatorRoster）

新增局内数据结构，跟踪玩家当前持有的干员及其状态：

```
RogueOperatorState
├── operatorDataId    (string)  — 对应 OperatorData 的名字/ID
├── starRating        (int)     — 星级（2/3/4）
├── level             (int)     — 当前等级（1~30/50/70，按星级）
├── promotion         (int)     — 精英化次数（0/1/2）
├── hopeCost          (int)     — 占用的希望值
└── isInitial         (bool)    — 是否初始干员（初始干员不占希望）
```

### 3.2 阵容上限

| 参数 | 值 | 说明 |
|------|-----|------|
| 初始携带上限 | 6 | 战斗中可同时部署的 OperatorCard 数量 |
| 最大携带上限 | 8 | 通过天赋树/事件可扩展 |
| 初始希望值 | 6 | 每局开始获得 |
| 最大希望值 | 12 | 通过事件/天赋树可扩展 |

> **希望值**是干员招募的容量货币（对标明日方舟 IS 的"希望"）。每次招募消耗希望，希望不足时无法招募。初始干员不消耗希望。

### 3.3 初始干员

每局开始时，玩家固定获得以下 4 名初始干员（不消耗希望）：

| 槽位 | 干员 | 星级 | 理由 |
|------|------|------|------|
| 初始先锋 | 斥候先锋 | ★★ | 低费回费，铺场起手 |
| 初始近战 | 战术先锋 | ★★★ | 中坚近战，可抗可打 |
| 初始远程 | 连弩 | ★★ | 远程输出入门 |
| 初始医疗 | 净化 | ★★ | 基础治疗保障 |

> 这 4 名干员即为"先锋测试"场景中角色画布的默认卡牌。随关卡推进，玩家可在商店/事件中招募更多干员替换或扩充。

### 3.4 战斗中的干员卡牌

- 战斗场景中的「角色画布」不再硬编码固定干员，改为**从 RogueRuntimeState.OperatorRoster 动态生成 OperatorCard**
- 携带上限决定可生成的卡牌数量（最多 6~8 张）
- 玩家在关卡间可以调整出战阵容（在 plot 地图界面操作）

## 四、干员招募系统

### 4.1 招募节点

招募在以下节点可用：

| 节点类型 | 招募方式 | 说明 |
|---------|---------|------|
| 商店（GoldShop） | 金币购买 | 商店新增"招募"分页，展示 3~4 个可招募干员 |
| 事件（RandomEvent） | 事件奖励 | 部分事件选项奖励干员（如"流浪战士加入"） |
| 关卡奖励 | 通关选择 | 精英/Boss 关通关后，选卡环节可替换为"招募干员"选项 |

### 4.2 商店招募（S5 招募服务）

在现有 GoldShopController 基础上新增招募分页：

| 参数 | 值 | 说明 |
|------|-----|------|
| 招募货位数量 | 4 | 每次进店展示 4 个可招募干员 |
| 刷新费用 | 与天赋卡刷新合并 | 共用 ShopRefreshBaseCost（10 金币起递增） |
| 招募价格（★★） | 20 金币 + 2 希望 | 低星干员便宜但希望消耗固定 |
| 招募价格（★★★） | 40 金币 + 3 希望 | 中坚干员 |
| 招募价格（★★★★） | 80 金币 + 4 希望 | 核心干员昂贵 |
| 招募池规则 | 排除已持有 | 重复干员不再出现在招募池 |
| 每店招募上限 | 3 次 | 每次进入商店最多招募 3 名干员 |

### 4.3 招募池构建

```
招募池 = 所有 OperatorData（29 个）
       - 当前已持有的干员
       - 按星级随机抽取 4 个展示
       - 星级权重：★★ 50% / ★★★ 35% / ★★★★ 15%
       - 随关卡深度，高星出现率温和提升（与经济膨胀同步）
```

### 4.4 招募 UI 流程

```
商店界面
  ├── [天赋卡] 分页（现有）
  └── [干员招募] 分页（新增）
        ├── 招募货位 × 4（显示干员立绘 + 星级 + 金币/希望消耗）
        ├── 当前希望值显示（★ ☆ ☆ ☆ ☆ ☆ → ★ ★ ★ ☆ ☆ ☆）
        ├── 当前阵容显示（已持有干员列表）
        └── [刷新] 按钮（金币刷新）
```

点击招募：
1. 检查希望值是否足够 → 不足则提示"希望不足"
2. 检查金币是否足够 → 不足则提示"金币不足"
3. 检查阵容是否已满（8 人）→ 已满则提示"阵容已满，请先放弃干员"
4. 扣除金币 + 希望，将干员加入 RogueOperatorState 列表
5. 货位标记为"已招募"

### 4.5 放弃干员

玩家可以在商店或地图界面放弃已持有的干员：
- 放弃干员返还 50% 金币（按招募价计算）
- 返还全部希望值
- 初始干员不可放弃

## 五、干员升级系统

### 5.1 等级与属性成长

| 星级 | 初始等级 | 升级上限（未精英化） | 精英 1 上限 | 精英 2 上限 |
|------|---------|-------------------|------------|------------|
| ★★ | 1 | 30 | 50 | — |
| ★★★ | 1 | 40 | 60 | 70 |
| ★★★★ | 1 | 50 | 70 | 80 |

### 5.2 属性成长公式

每次升级提升基础属性（百分比叠加于 OperatorData 原始值）：

```
升级后属性 = 基础属性 × (1 + (level - 1) × growthRate × starGrowthMultiplier)

growthRate = 0.04（每级 +4% 基础值）
starGrowthMultiplier: ★★ = 0.8, ★★★ = 1.0, ★★★★ = 1.3
```

| 属性 | 成长方向 |
|------|---------|
| maxHealth | 每级 +4% × starGrowthMultiplier |
| attackDamage | 每级 +4% × starGrowthMultiplier |
| defense | 每级 +3%（固定值加成，非百分比） |
| attackInterval | 不变 |
| attackRange | 不变（升星解锁） |
| cost | 不变 |

### 5.3 升级费用

| 当前等级段 | 单次升级金币 | 说明 |
|-----------|------------|------|
| 1→10 | 5 × 当前等级 | 前期便宜 |
| 11→20 | 8 × 当前等级 | 中期温和 |
| 21→30 | 12 × 当前等级 | 后期昂贵 |
| 31+ | 15 × 当前等级 | 精英化后 |

> 升级在商店/休息节点可用。每次升级 +1 级，即时生效。

### 5.4 升级 UI

```
干员详情面板（点击干员卡打开）
  ├── 干员立绘 + 星级 + 名称
  ├── 当前等级 / 上限
  ├── 属性面板（HP / 攻击 / 防御 / 射程 / 攻速）
  ├── [升级] 按钮（显示费用：XX 金币）
  ├── [精英化] 按钮（满足条件时高亮）
  └── [放弃] 按钮（初始干员禁用）
```

## 六、干员升星（精英化）系统

### 6.1 精英化机制

参考明日方舟精英化，分两阶段：

| 精英化阶段 | 解锁条件 | 效果 |
|-----------|---------|------|
| 精英 1 (Promotion 1) | 等级达到星级上限 | 等级重置为 1，等级上限提升，全属性 +10%，部署费用 +2 |
| 精英 2 (Promotion 2) | 精英 1 等级达上限（仅★★★/★★★★） | 等级重置为 1，等级上限提升，全属性 +25%，部署费用 +3，解锁强化被动 |

### 6.2 精英化费用

| 阶段 | ★★ | ★★★ | ★★★★ |
|------|-----|------|------|
| 精英 1 | 30 金币 + 1 希望 | 50 金币 + 1 希望 | 80 金币 + 2 希望 |
| 精英 2 | — | 100 金币 + 2 希望 | 150 金币 + 3 希望 |

> 精英化消耗的希望值是"追加投资"，不增加干员的常驻希望占用。即一名 ★★★ 精英 2 干员仍然只占 3 点希望。

### 6.3 精英化属性变化

```
精英 1 全属性 = 基础属性 × 1.10（固定 +10%）
精英 2 全属性 = 基础属性 × 1.25（固定 +25%，替代精英 1 的 +10%）
```

### 6.4 精英 2 强化被动（示例）

每个干员在精英 2 后解锁一个强化被动（不新增技能，仅增强已有机制）：

| 职业类型 | 精英 2 被动 | 效果 |
|---------|------------|------|
| 先锋 Vanguard | 回费精通 | 部署后立即回复 3 DP |
| 近卫 Guard | 专注强化 | 专注状态攻速加成从 ×1.5 提升到 ×1.8 |
| 重装 Defender | 钢铁意志 | 受到致命伤时保留 1 点生命（每场限 1 次） |
| 狙击 Sniper | 致命瞄准 | 暴击率 +10%，暴击伤害 +50% |
| 术师 Caster | 穿透精通 | 破甲比例 +15% |
| 医疗 Medic | 紧急救护 | 治疗目标 HP 低于 30% 时治疗量 +50% |
| 特种 Specialist | 战术机动 | 技能冷却 -20% |

> 精英 2 被动通过 OperatorUnit 的现有 TalentEffectApplier 系统注入，无需新增组件。在 OperatorUnit.Start() 中检查 promotion 状态，应用对应被动。

### 7.5 属性计算方法

```csharp
// 运行时获取干员当前属性（考虑等级 + 精英化）
public static float GetRuntimeMaxHealth(OperatorData data, int level, int promotion)
{
    float starMult = data.starRating switch { 2 => Star2GrowthMultiplier, 3 => Star3GrowthMultiplier, 4 => Star4GrowthMultiplier, _ => 1f };
    float promoMult = promotion switch { 1 => 1.10f, 2 => 1.25f, _ => 1f };
    return data.maxHealth * promoMult * (1f + (level - 1) * GrowthRatePerLevel * starMult);
}

// attackDamage 同理
// defense: 固定值加成
public static int GetRuntimeDefense(OperatorData data, int level, int promotion)
{
    float starMult = data.starRating switch { 2 => Star2GrowthMultiplier, 3 => Star3GrowthMultiplier, 4 => Star4GrowthMultiplier, _ => 1f };
    float promoMult = promotion switch { 1 => 1.10f, 2 => 1.25f, _ => 1f };
    return Mathf.RoundToInt(data.defense * promoMult * (1f + (level - 1) * 0.03f * starMult));
}
```

### 8.1 与天赋卡系统的关系

| 系统 | 作用对象 | 生效方式 | 叠加规则 |
|------|---------|---------|---------|
| 天赋卡 | 全队/职业/专属 | TalentEffectApplier 在 OperatorUnit.Start() 注入 | 百分比加成叠乘 |
| 天赋树 | 全队（永久） | TalentEffectApplier 在 OperatorUnit.Start() 注入 | 百分比加成叠乘 |
| 干员升级 | 单个干员 | OperatorUnit.Start() 读取 RogueOperatorState 计算 | 基础值放大，先于天赋卡 |

**计算顺序**：
```
最终属性 = (OperatorData 基础值 × 升级倍率 × 精英化倍率)  ← 干员升级
         × (1 + 天赋卡百分比加成)                        ← 天赋卡
         × (1 + 天赋树百分比加成)                        ← 天赋树
```

### 8.2 单实例部署机制（明日方舟式 · 核心改动）

#### 设计原理

现有系统中，同一干员冷却结束后可重复购买部署，且多个实例可同时在场。这在引入干员持有/升级/精英化系统后会导致：

1. **刷最优解**：玩家只需招募 1~2 个最强干员反复刷，阵容多样性无意义
2. **数值失控**：多个升级后的高属性实例同时在场，DPS/防御总量远超设计预期
3. **策略扁平**："带哪些干员"不再重要，变成"谁的 DP 效率最高就刷谁"

**解决方案（方案 B）**：完全采用明日方舟式部署规则——每名干员同时**只能有 1 个实例在场**。无论主动撤退还是阵亡，都需要等待**再部署冷却**结束后才能再次部署该干员。

#### 核心规则

| 规则 | 说明 |
|------|------|
| 单实例 | 同一干员在场时，其 OperatorCard 灰化不可拖拽，显示"部署中" |
| 撤退 | 主动撤退后，干员离开战场，卡牌进入再部署冷却（返还部分 DP） |
| 阵亡 | 被击杀后，卡牌进入再部署冷却（不返还 DP），冷却时间通常比撤退更长 |
| 再部署冷却 | 复用现有 `purchaseCooldown` 字段；阵亡时的冷却 = purchaseCooldown × 1.5 |
| 冷却结束 | 卡牌恢复可用状态，可再次部署（扣全额 DP） |

#### 撤退与阵亡的冷却区分

| 情况 | 再部署冷却 | DP 返还 | 说明 |
|------|-----------|---------|------|
| 主动撤退 | `purchaseCooldown` | 返还 50% 已消耗 DP | 战术性撤回，惩罚较轻 |
| 阵亡 | `purchaseCooldown × 1.5` | 不返还 DP | 惩罚更重，让玩家珍惜站位 |
| 正常部署 | — | 扣除全额 DP | 现有逻辑不变 |

> **设计意图**：撤退和阵亡的冷却差异让玩家有动力主动撤退（"及时止损"），而不是让干员白白送死。这也让低费干员的定位更清晰——它们 purchaseCooldown 短，即使阵亡也很快能重新部署，适合当炮灰/诱饵。

#### 撤退系统变更

现有 DeploymentManager 已有撤退模式（`isRetreatMode` / `ToggleRetreatMode()` / `HandleRetreatInput()`），需要扩展：

```csharp
// 撤退干员时调用
public void RetreatOperator(OperatorUnit unit)
{
    // 返还 50% DP
    int refund = Mathf.RoundToInt(unit.DeployedCost * 0.5f);
    AddDP(refund);
    
    // 触发再部署冷却（正常 purchaseCooldown）
    var card = FindOperatorCard(unit.data.operatorName);
    if (card != null)
        card.StartRedeployCooldown(unit.data.purchaseCooldown);

    unit.OnRetreat(); // 设置 IsRetreating = true，播放撤退动画后销毁
}

// 干员阵亡时调用（由 OperatorUnit.Die() 触发）
public void OnOperatorDied(OperatorUnit unit)
{
    // 不返还 DP
    // 触发再部署冷却（purchaseCooldown × 1.5）
    var card = FindOperatorCard(unit.data.operatorName);
    if (card != null)
        card.StartRedeployCooldown(unit.data.purchaseCooldown * 1.5f);
}
```

#### 对低费干员的影响与补偿

方案 B 对低费干员（突击先锋 cost=3, purchaseCooldown=15s）影响最大——不能再同时铺 3 个堵路。补偿措施：

| 措施 | 说明 |
|------|------|
| 低再部署冷却 | 低费干员 purchaseCooldown 本就短（15s），阵亡后 22.5s 即可重新部署 |
| 撤退返还 DP | 撤退返还 50% DP，低费干员撤退几乎不亏经济 |
| 低费 = 高频轮换 | 低费干员的定位从"同时铺多个"变为"高频轮换部署"，阵亡/撤退后快速回场 |
| 携带数量上限提高 | 阵容上限 6~8 名，确保玩家有足够多的不同干员轮换 |

> 这也让携带更多不同干员成为刚需——既然每个干员只能放 1 个，那 6 张卡牌 = 最多 6 个干员同时在战场，玩家必须通过招募扩充阵容才能应对多路线敌人。

### 9.3 与天赋卡系统的资源分配

天赋卡和干员招募共用金币，形成消费竞争：
- **天赋卡路线**：投资在全队加成，适合已有强力干员的 build
- **干员招募路线**：投资在干员数量和质量，适合需要补短板的 build
- **升级路线**：投资在已有干员的属性提升，性价比稳定但上限有限

三者之间的金币分配是核心策略决策点。

## 十四、FAQ

**Q: 为什么不用永久干员等级（通关后保留）？**
A: 肉鸽模式的核心理念是"每局从零开始"。永久等级会破坏肉鸽的重玩价值。永久成长已由天赋树系统覆盖。

**Q: 现有场景中的 5 张固定 OperatorCard 怎么办？**
A: 改为动态生成。战斗场景初始化时从 RogueRuntimeState.OperatorRoster 读取，按携带上限生成对应数量的 OperatorCard。现有角色画布作为容器，子对象由代码生成。

**Q: 醒（cost=0, 20000HP, 600s 冷却）怎么处理？**
A: 作为特殊隐藏干员，不进入常规招募池。仅通过特殊事件/Boss 奖励获得。

**Q: 为什么选择方案 B（明日方舟式单实例）而不是保留多实例？**
A: 单实例让每一名干员都有不可替代性——你不能再靠刷 3 个相同低费干员堵路，必须招募不同干员应对多路线敌人。这直接驱动了招募系统的策略价值。低费干员的定位从"同时铺多个"变为"高频轮换"——purchaseCooldown 短（15s），阵亡后 22.5s 即可重新部署，撤退还返还 50% DP，经济上几乎不亏。

**Q: 撤退和阵亡的区别是什么？**
A: 主动撤退返还 50% DP，再部署冷却 = purchaseCooldown（正常值）。阵亡不返还 DP，再部署冷却 = purchaseCooldown × 1.5（惩罚性延长）。这让玩家有动力主动撤退及时止损，而不是让干员白白送死。

**Q: 现有的 purchaseCooldown 字段怎么用？**
A: purchaseCooldown 语义变更为"再部署冷却"。干员在场时卡牌灰化显示"部署中"；撤退/阵亡后卡牌进入再部署冷却倒计时；冷却结束后可重新部署（扣全额 DP）。原有的冷却 overlay 进度条机制完全复用。

**Q: 天赋卡的 ByOperator 作用范围怎么和升级系统配合？**
A: 天赋卡 ByOperator 仍然按 operatorName 匹配，不受等级/精英化影响。升级改变基础属性，天赋卡改变百分比加成，两者独立计算后叠乘。

**Q: 放弃干员后重新招募能找回吗？**
A: 可以。放弃后干员回到招募池，有概率再次出现在商店招募货位中。但需要重新花费金币+希望。
