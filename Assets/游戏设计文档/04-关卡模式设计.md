# 关卡模式设计（固定 / 混合 / 双模式）

> 本文档记录关卡“确定性 vs 随机性”的设计方向，作为后续实现的依据。
> 当前（2026-07-31）**固定关卡模式代码已落地但未导出数据**，**混合模式代码已实现**，双模式开关待 UI，本文仅作设计存档与复杂度评估。
>
> 关联文档：`01-游戏设计总纲.md`（节点系统）、`03-数值配置与平衡参考.md`（平衡基准）。
> 关联代码：`Assets/塔防脚本/关卡与生成/LevelConfig.cs`、`关卡选择/LevelNodeButton.cs`、`Editor/LevelConfigExporter.cs`、`地图/BattleSceneBootstrap.cs`。
> 混合模式新增代码：`GameMode.cs`、`RunRng.cs`、`RunModifierConfig.cs`、`LevelRunModifiers.cs`。

## 1. 设计目标

- 用**一份战斗引擎 + 每关一份数据（LevelConfig.asset）**取代“每关一个独立场景”的旧架构（详见 `01` 与历史重构记录）。
- 关卡体验的底线是**可维护、难度可设、数值不崩溃**；随机性作为“提升重复可玩性”的增量，而非破坏设计确定性的来源。
- 短期：固定关卡跑通。
- 中期可选项：前几关固定、后段引入随机（混合模式）。
- 长期可选项：提供“固定模式 / 随机模式”双模式给玩家选择。

---

## 2. 模式一：固定关卡模式（当前默认，已落地）

**定义**：每一关有一份手调的 `LevelConfig.asset`，包含确定的地图布局、敌人路线、波次结构、难度修饰符。每次进入同一关，内容完全一致。

**数据位置**：`Assets/Resources/LevelConfigs/Level_{N:D2}_Battle.asset`
**导出方式**：Unity 编辑器 → `Tools → 批量导出所有关卡场景`（一键把现有 `level N.unity` 抽成固定配置）。

**现状**：
- `BattleScene.unity` 与 `MapBuilder` / `BattleSceneBootstrap` 已就绪，**但尚未导出任何 `.asset`**。
- 因此当前所有关卡按钮仍走旧 `level N` 场景回退（`LevelNodeButton.OnClick` 中 `_cachedLevelConfig == null` 时加载旧场景）。
- 跑通固定模式的**唯一剩余动作** = 在编辑器执行一次批量导出。这一步成本低、风险小。

**固定模式保留的“轻随机”空间**（不破坏确定性，已预留字段）：
`LevelConfig.cs` 中的修饰符字段可在运行时被天赋/卡牌/难度系统改写，但**不改变源 `.asset`**：
- `availableEnemyTypes`（敌人池）
- `enemyHpMultiplier` / `enemySpeedMultiplier`（倍率）
- `startDP` / `maxLifePoint`（费用与守护点）

> 结论：**固定关卡模式本身完全可行**，它提供“保底体验 + 可控难度 + 易维护”，是其它模式的基础。

---

## 3. 模式二：混合模式（前 N 关固定，后段随机）

**定义**：按关卡序号分段——前 N 关（如 1~5）强制使用固定 `LevelConfig.asset`，保证新手教学与节奏稳定；第 N+1 关起，进入关卡时在固定结构之上叠加**受控随机修饰**。

**随机只作用在“修饰层”，不动结构层**：
- 结构层（地图布局、路线、波次节奏）保持固定 → 难度曲线仍由设计师手控，可测试。
- 随机层（在 `LevelConfig` 副本上叠加，永不写回源 asset）：
  - 敌人组合：从本关 `availableEnemyTypes` 池按权重抽取具体兵种（地图不变、兵种变）。
  - 难度修饰：在**设计区间**内抖动 `enemyHpMultiplier` / `enemySpeedMultiplier` / `startDP`，如 `Hp ∈ [1.0, 1.3]`。
  - 用**种子（seed）驱动**，保证同一局内可复现、便于调试。

**启用判断（伪逻辑）**：
```
进关时：
  if levelNumber <= FixedCutoff:  用固定 LevelConfig.asset
  else:                           用 base asset 的副本 + ApplyRunModifiers(seed, levelNumber)
```

**防数值崩溃的三道保险**（必须遵守）：
1. 随机不打结构，只打修饰符。
2. 用**区间/权重表**而非裸随机；倍率区间由 `03-数值配置与平衡参考` 收敛。
3. 随机结果作用在运行时副本，源 `.asset` 始终为“平衡真理”，回滚一眼可见。

---

## 4. 模式三：双模式（固定模式 / 随机模式，玩家可选）

**定义**：在开局/选关界面提供模式开关。
- **固定模式**：等同模式一（全部用固定 `LevelConfig.asset`）。
- **随机模式**：全部关卡（或 Boss/精英外）在固定结构之上叠加受控随机修饰（复用模式二的随机层）。

**与混合模式的关系**：二者是同一套“随机化修饰层”的两种开关形态——
- 混合模式 = 按关卡序号阈值自动开关随机；
- 双模式 = 按玩家选择全局开关随机。
底层随机化能力只需实现一次，两种模式只是不同的“启用区间/开关”。

## 5. 实现复杂度评估（是否现在做）

| 能力 | 复杂度 | 主要工作量 | 风险 | 建议 |
|------|--------|-----------|------|------|
| 固定模式跑通（导出 `.asset`） | 易 | 编辑器一键导出 + 验证跳转 | 低 | **现在做**（剩余动作极少） |
| 混合模式（前 N 固定 + 后段修饰层随机） | 中 | 进关分支判断 + `ApplyRunModifiers` + 敌人池/倍率区间表 | 低（不碰地图生成） | 中期做；复用现有字段，不破坏数值 |
| 双模式（玩家可选开关） | 中 | 在混合模式基础上加模式枚举 + 开局 UI 开关 | 低 | 与混合模式同批或稍后，底层复用 |
| **随机模式含“地图随机生成”** | **难** | 地图随机生成需保证连通性、路径不交叉、部署位/高台位充足、可解性验证 | **高**（算法+平衡验证） | **以后再做**；非本设计必选项 |

> 判定结论：
> - 你担心的“随机性太高导致数值崩溃”可通过**只随机修饰层 + 区间约束 + 副本隔离**规避，技术上不难。
> - 真正难的是“地图随机生成”（保证每局地图既不同又可通关），这属于随机模式的进阶形态，**不在当前必须项内**，按你的意思先写进设计、日后视情况再搞。

## 6. 落地优先级与触发条件

1. **P0（现在）**：执行 `Tools → 批量导出所有关卡场景`，验证 `BattleScene` 跳转与战斗正常。固定模式即生效。
2. **P1（中期，体验需要重复可玩性时）**：实现 `ApplyRunModifiers(seed, level)` 与敌人池抽取，接入进关流程，先上“混合模式”（前 N 固定 + 后段随机）。
3. **P2（玩家有模式选择诉求时）**：在 P1 之上加 `GameMode { Fixed, Random }` 枚举与开局开关，升级为双模式。
4. **P3（以后，非必选）**：若要做“每局地图都不同”的完整随机模式，再单独立项研究地图随机生成与可解性验证。

## 7. 技术挂钩点速查（实现时直接改这些）

- 进关分支：`LevelNodeButton.OnClick()`（`_cachedLevelConfig` 判断处）增加“序号阈值 / 模式开关”判断。
- 随机修饰入口：新增 `LevelConfig.ApplyRunModifiers(RunRng rng, int levelNumber)`，作用在 `LevelConfig` 运行时副本（不写回 `.asset`）。
- 敌人池抽卡：在 `LevelConfig.FlattenToWaveDataList()` 阶段按 `availableEnemyTypes` 权重抽取具体 `enemyType`。
- 模式枚举：在 `RogueRuntimeState` 或 `GameManager` 增加 `GameMode` 字段，供开局 UI 与进关流程读取。
- 难度区间表：倍率上下限定义在 `03-数值配置与平衡参考.md` 收敛，代码侧只读引用。
